# Output Structure

File output locations and structure for documentation generation.

## Directory Structure

```
docs/
├── services/
│   ├── <service-name>/
│   │   ├── features.md          # Marketing-ready
│   │   ├── technical.md         # Developer reference
│   │   ├── tutorial.md          # Getting-started guide
│   │   ├── technical-debt.md    # Debt tracking
│   │   └── agent.md             # Machine-readable (autonomous only)
│   └── index.md                 # Service catalog
├── packages/
│   └── <package-name>/
│       ├── README.md            # Overview, API, dependencies, usage
│       ├── technical-debt.md    # Debt tracking
│       └── agent.md             # Machine-readable interface
├── validation/
│   ├── http-contracts-validation.md
│   ├── pubsub-contracts-validation.md
│   ├── ai-models-validation.md
│   ├── firestore-validation.md
│   ├── package-deps-validation.md
│   ├── env-vars-validation.md
│   └── v<version>-documentation-run-report.md
├── overview.md                  # Project narrative
├── documentation-runs.md        # Run history log
└── site-index.json              # Structured metadata
```

## Validation Report Files (7 total)

### Per-Domain Reports

**Location:** `docs/validation/<domain>-validation.md`
**Purpose:** Cross-service consistency check for a specific domain
**Generated by:** Cross-validation agents (Phase 4 of team workflow)
**Domains:** HTTP contracts, Pub/Sub contracts, AI models, Firestore collections, Package dependencies, Environment variables

### Run Report

**Location:** `docs/validation/v<version>-documentation-run-report.md`
**Purpose:** Comprehensive summary of a full documentation run
**Generated by:** Orchestrator after all phases complete
**Sections:** Executive summary, discovery results, generation summary, aggregation changes, validation findings, systemic patterns, recommendations, agent execution summary

## Aggregated Files

### services/index.md

**Location:** `docs/services/index.md`
**Purpose:** Service catalog listing all services, workers, and packages
**Update Rule:** Incremental -- add documented services, remove from pending

**Sections:**

- Documented Services (with links)
- Workers (with links)
- Packages (with links)
- Pending Documentation (checklist)

### overview.md

**Location:** `docs/overview.md`
**Purpose:** Project narrative and architecture overview
**Update Rule:** Update when service adds new capability category

**Sections:**

- What is IntexuraOS
- How It Works (by problem category)
- Services table
- Worker Architecture
- Package Ecosystem
- Getting Started
- Architecture

### documentation-runs.md

**Location:** `docs/documentation-runs.md`
**Purpose:** Log of all documentation runs
**Update Rule:** Append only -- never modify existing entries

**Entry Format:**

```markdown
## YYYY-MM-DD - <service-name or version>

**Action:** [Created | Updated]
**Agent:** [document-service | service-scribe | team]
**Files:** [list]
**Coverage:** N%
**Debt Found:** [counts]
```

### site-index.json

**Location:** `docs/site-index.json`
**Purpose:** Structured metadata for site build
**Update Rule:** Append service/package to array, update stats

**Schema:**

```json
{
  "lastUpdated": "YYYY-MM-DD",
  "services": [
    {
      "id": "service-name",
      "name": "Service Display Name",
      "tagline": "One line description",
      "category": "agents | infrastructure | workers | packages",
      "features": "Key features list",
      "status": "documented | pending",
      "lastUpdated": "YYYY-MM-DD",
      "docs": {
        "features": "services/service-name/features.md",
        "technical": "services/service-name/technical.md",
        "debt": "services/service-name/technical-debt.md"
      }
    }
  ],
  "stats": {
    "totalServices": 25,
    "totalWorkers": 5,
    "totalPackages": 21,
    "documentedServices": 25,
    "completion": "100%"
  }
}
```

## Incremental Update Rules

### Adding a New Service (App or Worker)

1. Create service directory: `docs/services/<service-name>/`
2. Generate 5 files in service directory
3. Update `services/index.md`: add to appropriate section
4. Update `site-index.json`: append service, update stats
5. Update `overview.md` if service adds new capability category
6. Append entry to `documentation-runs.md`

### Adding a New Package

1. Create package directory: `docs/packages/<package-name>/`
2. Generate 3 files in package directory
3. Update `services/index.md`: add to Packages section
4. Update `site-index.json`: append to packages array
5. Append entry to `documentation-runs.md`

### Updating Existing Service

1. Regenerate service files (preserve user insights)
2. Update `documentation-runs.md` with new entry
3. If debt items resolved, move to "Resolved Issues"
4. If new capabilities, update aggregation files

### Running Cross-Validation

1. Generate validation reports in `docs/validation/`
2. Generate run report in `docs/validation/v<version>-documentation-run-report.md`
3. Reports are standalone -- they don't modify service docs
4. Fixing discrepancies found in validation is a separate task

## File Linking Conventions

### Within Service Docs

```markdown
See [Technical Reference](technical.md) for API details.
See [Features](features.md) for capabilities.
```

### To Other Services

```markdown
Works with [WhatsApp Service](../whatsapp-service/features.md)
```

### To Package Docs

```markdown
Uses [@intexuraos/common-core](../../packages/common-core/README.md)
```

### To Project Docs

```markdown
Part of [IntexuraOS](../../overview.md)
Run log: [documentation-runs.md](../../documentation-runs.md)
```

### To Validation Reports

```markdown
See [HTTP Contracts Validation](../../validation/http-contracts-validation.md)
```

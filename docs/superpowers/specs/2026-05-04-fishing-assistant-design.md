# Fishing Assistant RAG Design

**Date:** 2026-05-04
**Status:** Draft for review
**Primary Service:** `fishing-assistant-service`
**Related Service:** `mobile-notifications-service`
**Audience:** Implementation worker building the new service, required mobile notification APIs, and web UI

## Purpose

Build a per-user Fishing Assistant that answers questions from the user's private fishing knowledge, daily WhatsApp digest summaries, and quoted raw mobile notification messages.

The assistant must support:

- a persisted Knowledge Base with full folder and page CRUD
- automatic normalization, chunking, and embedding of pasted page content
- persisted chat sessions that users can reopen and continue
- RAG answers generated by Gemini 3 Flash through OpenRouter
- strict linked citations for every factual answer
- Current Digests access inside the Fishing Assistant navigation

This is a fishing-domain RAG assistant. It is not related to cybersecurity or phishing.

## Decision Summary

Use Approach A: create a standalone `fishing-assistant-service`.

The new service owns:

- Fishing Assistant folders
- Knowledge Base pages
- normalized chunks and embeddings
- chat sessions and messages
- retrieval, reranking, prompt construction, citation validation, and chat persistence

The new service does not own mobile notification storage or digest generation. It calls `mobile-notifications-service` through internal APIs for digest and raw-message evidence.

## Key Product Decisions

- Data is strictly per-user.
- Knowledge Base input is manual copy-paste only.
- The hierarchy is intentionally simple: `Folder -> Page`.
- Users can create, edit, display, and delete folders and pages.
- Chat sessions are persisted and can be continued later.
- Chat sessions do not need delete, rename, or archive in v1.
- Chat answers require evidence. If no evidence exists, the assistant must say it does not have enough evidence.
- Raw mobile messages are cited as quotes with dates, not as full message records or separate pages.
- Existing web UI patterns from Code Tasks and Hellscript must be followed.
- Seed import from fetched Skool data must be included as an implementation option, but only run when explicitly requested during development.

## Service Boundary

`fishing-assistant-service` is a user-facing domain service.

It is responsible for:

1. Knowledge Base CRUD.
2. Page title inference.
3. Page normalization.
4. Structure-aware chunking.
5. Embedding generation and storage.
6. Vector retrieval over per-user chunks.
7. Digest and raw-message retrieval through mobile notification internal APIs.
8. Evidence merging and reranking.
9. Gemini 3 Flash chat generation.
10. Citation validation.
11. Chat session and message persistence.

It is not responsible for:

- mobile notification ingestion
- digest generation
- WhatsApp group subscription ownership
- storing raw notification records
- storing user API keys
- exposing Skool automation in the UI

## API Key Policy

### Chat Generation

Chat generation must use:

```text
or:google/gemini-3-flash-preview
```

This model is currently routed through OpenRouter in this repo.

Rules:

- use the user's OpenRouter API key
- do not fall back to a platform OpenRouter key
- if the user has no OpenRouter key, return `NO_API_KEY`
- never expose API keys to the browser

The service should resolve the user's OpenRouter key through User Service internal APIs. The existing `getLlmClient(userId)` method is not sufficient for chat because it uses the user's default model. Fishing Assistant chat has a fixed model requirement, so the implementation should add or locally implement a model-specific resolver.

### Title Inference

Title inference uses the user's default LLM from User Service only when deterministic header extraction fails.

### Embeddings

Embeddings use a service-level OpenAI key.

Rules:

- use `text-embedding-3-small`
- store 1536-dimensional vectors
- do not require every user to configure OpenAI
- do not use the user's OpenAI key for embeddings in v1

## Firestore Data Model

All records are strictly scoped by `userId`.

Collections:

```text
fishing_knowledge_folders
fishing_knowledge_pages
fishing_knowledge_chunks
fishing_chats
fishing_chat_messages
```

Every new collection must be registered in `firestore-collections.json`.

### `fishing_knowledge_folders`

```ts
{
  id: string;
  userId: string;
  name: string;
  createdAt: Timestamp;
  updatedAt: Timestamp;
  pageCount: number;
}
```

Folder names only need to be unique per user in v1 if the implementation can enforce it simply. Duplicate names are not a security issue, but unique names improve UX.

### `fishing_knowledge_pages`

```ts
{
  id: string;
  userId: string;
  folderId: string;
  title: string;
  titleSource: "header" | "llm" | "manual";
  rawText: string;
  normalizedText: string;
  tags: string[];
  contentType: "recipe" | "guide" | "species" | "theory" | "additive" | "qna" | "other";
  indexingStatus: "ready" | "failed";
  createdAt: Timestamp;
  updatedAt: Timestamp;
}
```

`rawText` preserves the exact pasted content for display and full-page follow-up answers.

### `fishing_knowledge_chunks`

```ts
{
  id: string;
  userId: string;
  folderId: string;
  pageId: string;
  pageTitle: string;
  folderName: string;
  heading: string | null;
  chunkIndex: number;
  text: string;
  searchableText: string;
  tags: string[];
  embedding: vector<1536>;
  embeddingModel: "text-embedding-3-small";
  createdAt: Timestamp;
  updatedAt: Timestamp;
}
```

Vector queries must always be scoped to `userId`. If Firestore vector query limitations make direct `where('userId', '==', userId)` difficult, the implementation must either use a supported pre-filter pattern or query more results and enforce `userId` after retrieval. Under no circumstances can cross-user chunks be returned to prompt construction.

### `fishing_chats`

```ts
{
  id: string;
  userId: string;
  title: string;
  createdAt: Timestamp;
  updatedAt: Timestamp;
  lastMessageAt: Timestamp;
  messageCount: number;
}
```

Chat title can use deterministic first-message shortening. Use the user's default LLM only if the first message is too long or unclear.

### `fishing_chat_messages`

```ts
{
  id: string;
  userId: string;
  chatId: string;
  role: "user" | "assistant";
  content: string;
  createdAt: Timestamp;

  modelId?: "or:google/gemini-3-flash-preview";
  citations?: Citation[];

```

## Knowledge Base Save Flow

The UI only supports manual paste.

Save flow:

1. User chooses or creates a folder.
2. User pastes page content.
3. Backend infers title.
4. Backend normalizes text.
5. Backend chunks content.
6. Backend embeds chunks.
7. Backend stores page and chunks.

Title inference:

1. Use the first non-empty line if it looks header-like.
2. If no reliable header exists, use the user's default LLM from User Service.
3. Allow manual title override from the page editor.

If embedding fails:

- save the page anyway
- set `indexingStatus: "failed"`
- do not store partial vector evidence for that page unless every chunk has a valid embedding
- expose a reindex action

## Normalization And Chunking

Use structure-aware deterministic chunking, not LLM chunking.

Normalization should:

- trim extra whitespace
- normalize bullet spacing
- preserve Polish characters
- preserve units and numeric quantities
- detect headings
- extract broad tags
- infer broad `contentType`

Content type is intentionally broad:

```ts
"recipe" | "guide" | "species" | "theory" | "additive" | "qna" | "other"
```

Examples of supported knowledge topics:

- recipes and boosters
- method feeder, feeder, and float setup guides
- species profiles
- bait theory
- water zones and fish behavior
- bottom structure
- liquid additives
- competition prep
- live session notes
- general theory

Chunking rules:

- split by detected headings first
- keep bullets under their heading
- split oversized sections only when needed
- target chunk size: 800-1200 characters
- maximum chunk size: 1600 characters
- overlap: 100-150 characters or last 1-2 sentences
- prepend page context into `searchableText`

Example `searchableText`:

```text
Folder: Zanęty
Page: Zanęta delikatna
Heading: Fermentacja i sygnał chemiczny

100 g zmielonej kukurydzy z własnej fermentacji...
```

## Retrieval Design

Each chat question builds one evidence set from three sources:

1. Knowledge Base chunks.
2. Daily digest summaries.
3. Raw mobile message snippets.

Retrieval flow:

```text
question
  -> embed question
  -> vector search KB chunks
  -> query digest summaries for matching terms/date context
  -> fetch raw message snippets for strongest dates/terms
  -> merge and rerank evidence
  -> send top evidence blocks to Gemini
```

Initial limits:

- retrieve top 8-12 KB chunks by vector similarity
- retrieve top 5-8 digest matches
- retrieve raw messages only from the strongest dates or explicit date range
- cap final prompt evidence to avoid flooding Gemini

Knowledge Base evidence usually has highest authority for exact recipes and concepts. Digests and raw messages prove what the group discussed and tested.

## Unified Evidence Block

The Fishing Assistant service should convert all sources into one evidence format before prompt construction.

```ts
{
  id: string;
  sourceType: "knowledge_page" | "digest" | "raw_message";
  title: string;
  date?: string;
  heading?: string;
  text: string;
  quote: string;
  url?: string;
  metadata?: Record<string, unknown>;
}
```

Knowledge page example:

```ts
{
  id: "kb:page_123:chunk_3",
  sourceType: "knowledge_page",
  title: "Zanęta delikatna",
  heading: "Fermentacja i sygnał chemiczny",
  text: "...",
  quote: "100 g zmielonej kukurydzy z własnej fermentacji...",
  url: "/fishing-assistant/knowledge/pages/page_123"
}
```

Digest example:

```ts
{
  id: "digest:grupa-wedkarska-skool:2026-04-04",
  sourceType: "digest",
  title: "Digest 2026-04-04",
  date: "2026-04-04",
  text: "...flattened digest summary...",
  quote: "...short digest quote...",
  url: "/fishing-assistant/digests/grupa-wedkarska-skool/2026-04-04"
}
```

Raw message example:

```ts
{
  id: "raw:2026-04-04:abc123",
  sourceType: "raw_message",
  title: "Group message",
  date: "2026-04-04",
  text: "Pod płoć to spróbował bym raczej konopi kokos.",
  quote: "Pod płoć to spróbował bym raczej konopi kokos."
}
```

## Follow-Up Expansion

Chat must support follow-up requests such as:

```text
Give me the full recipe.
```

Flow:

1. Load recent chat messages.
2. Load previous assistant citations.
3. Detect follow-up expansion intent.
4. If one prior cited Knowledge Base page is dominant, fetch the full page.
5. If several pages are plausible, ask a short clarification.
6. Generate the answer from the expanded page evidence.

Assistant citation records must store stable page and chunk identifiers:

```ts
{
  sourceId: "S1";
  sourceType: "knowledge_page";
  pageId: "page_123";
  chunkId?: "chunk_456";
  title: "Zanęta delikatna";
  heading?: "Fermentacja i sygnał chemiczny";
  quote: string;
}
```

## Chat Generation And Citation Validation

Prompt rules:

- answer only from supplied evidence
- every factual claim must cite evidence IDs
- do not invent citation IDs
- if evidence is weak or missing, say so
- do not use web search
- respond in the user's language

Preferred model output:

```ts
{
  answerMarkdown: string;
  citations: Array<{
    sourceId: string;
    usedFor: string;
  }>;
  confidence: "high" | "medium" | "low";
}
```

Backend validation:

- every cited source ID must exist in the retrieved evidence set
- the answer must have at least one citation unless it explicitly says evidence is insufficient
- invalid citation output gets one repair attempt
- if repair fails, fail safely and do not show an uncited answer

## Fishing Assistant Public API

All routes are authenticated user routes.

```text
GET    /fishing/folders
POST   /fishing/folders
PATCH  /fishing/folders/:folderId
DELETE /fishing/folders/:folderId

GET    /fishing/pages
POST   /fishing/pages
GET    /fishing/pages/:pageId
PATCH  /fishing/pages/:pageId
DELETE /fishing/pages/:pageId
POST   /fishing/pages/:pageId/reindex

GET    /fishing/chats
POST   /fishing/chats
GET    /fishing/chats/:chatId
GET    /fishing/chats/:chatId/messages
POST   /fishing/chats/:chatId/messages

GET    /fishing/digests
GET    /fishing/digests/:groupKey/:date
```

Folder delete behavior:

- allow delete only when the folder has no pages
- return `409 FOLDER_NOT_EMPTY` otherwise

Page delete behavior:

- delete the page and its chunks
- update folder `pageCount`

Chat message behavior:

1. append user message
2. retrieve evidence
3. call Gemini
4. validate citations
5. append assistant message
6. update chat summary fields

## Required Mobile Notification Internal APIs

The current mobile notification API is not sufficient for Fishing Assistant retrieval.

Existing route:

```text
POST /internal/mobile-notifications/query
```

Current limitations:

- no date range
- no digest lookup
- no cursor in internal response
- no body/text filtering
- no cleaned group-message format
- no deduped group evidence output

Existing user-facing digest routes cannot be used by the new service because they require Auth0 user auth rather than service-to-service auth.

Add these internal routes to `mobile-notifications-service`.

### `POST /internal/notifications/digest-subscriptions/list`

Request:

```ts
{
  userId: string;
}
```

Response:

```ts
{
  items: Array<{
    groupKey: string;
    displayName: string;
  }>;
}
```

Implementation:

- validate `x-internal-auth`
- filter `getServices().digestSubscriptions` by `userId`
- return only `groupKey` and display label
- do not expose internal matching prefixes unless required later

Initial `displayName` can be `groupKey` or `groupTitlePrefix`. Prefer `groupTitlePrefix` if available.

### `POST /internal/notifications/digests/query`

Request:

```ts
{
  userId: string;
  groupKey: string;
  fromDate: string;
  toDate: string;
  limit?: number;
  cursor?: string;
}
```

Response:

```ts
{
  items: PersistedDailySummary[];
  nextCursor?: string;
}
```

Implementation:

- validate `x-internal-auth`
- validate subscription exists for `userId + groupKey`
- validate date format and `fromDate <= toDate`
- clamp `limit` to a safe maximum, likely 100
- call `digestRepository.findInRange(...)`

### `POST /internal/notifications/digests/get`

Request:

```ts
{
  userId: string;
  groupKey: string;
  date: string;
}
```

Response:

```ts
{
  digest: PersistedDailySummary;
}
```

Implementation:

- validate `x-internal-auth`
- validate subscription exists
- call `digestRepository.findByDate(...)`
- return 404 if missing

### `POST /internal/notifications/digests/state/get`

Request:

```ts
{
  userId: string;
  groupKey: string;
  date: string;
}
```

Response:

```ts
{
  state: GroupState;
}
```

Implementation:

- validate `x-internal-auth`
- validate subscription exists
- call `groupStateRepository.getByDate(...)`
- return 404 if missing

### `POST /internal/mobile-notifications/group-messages/query`

Request:

```ts
{
  userId: string;
  groupKey: string;
  dates?: string[];
  fromDate?: string;
  toDate?: string;
  terms?: string[];
  limit?: number;
}
```

Validation:

- require either `dates` or both `fromDate` and `toDate`
- reject requests containing both `dates` and range fields unless the implementation explicitly supports merging
- validate `YYYY-MM-DD` dates
- validate `fromDate <= toDate`
- cap date span, e.g. 31 days
- cap `dates` count, e.g. 31
- cap `terms` count and term length
- cap `limit`, likely 200

Response:

```ts
{
  messages: Array<{
    messageRef: string;
    groupKey: string;
    date: string;
    postTimeSec: number;
    senderLabel?: string | null;
    text: string;
    quote: string;
  }>;
  totalRaw: number;
  totalCleaned: number;
  returned: number;
  truncated: boolean;
}
```

Implementation:

- validate `x-internal-auth`
- validate subscription exists
- use the subscription's `groupTitlePrefix`
- query `notificationRepository.findByUserIdPaginated(...)`
- filter `app: ['com.whatsapp']`
- filter title by group title prefix
- use CET bounds from `cetDayBounds(date)`
- use `postTimeSecFrom` and `postTimeSecTo`
- apply `filterAndDedupeNotifications(...)`
- apply optional term filtering after cleanup
- return oldest-to-newest messages unless caller asks otherwise later

Important data-shape detail:

Real `mobile_notifications` documents have no formal `sender` field. They store:

```text
app, device, notificationId, postTime, receivedAt, source, text, timestamp, title, userId
```

Therefore `senderLabel` must be optional. If sender cannot be reliably parsed, return `null`. Do not make sender required for citations.

`messageRef` should be stable but not leak the full notification record. It can be derived from date, postTimeSec, and a short hash of text/title.

## Seed Import

The implementation plan should include an optional seed import task for the already fetched Skool-derived normalized text index.

Rules:

- do not run seed import unless the user explicitly asks during implementation
- seed folders from fetched top-level names
- seed pages into those folders
- run the same normalization/chunking/embedding path as manual pages
- do not store Skool auth cookies, raw JSON with tokens, or video metadata

The safer seed input is the token-free text index, not the raw authenticated capture.

## Error Handling

Missing user OpenRouter key:

- chat endpoint returns `NO_API_KEY`
- UI links to API Keys settings

No evidence:

- store assistant answer saying there is not enough evidence
- no citations
- no fabricated answer

Embedding failure:

- save page
- mark `indexingStatus: "failed"`
- show reindex action

Mobile notification service unavailable:

- chat can still answer from Knowledge Base evidence
- assistant should mention digest/message evidence was unavailable when relevant

Citation validation failure:

- attempt one repair
- fail safely if repair fails

## Open Implementation Notes

- The implementation should decide whether Fishing Assistant digest pages proxy existing digest components or create thin new wrappers. Prefer reuse.
- The implementation should verify Firestore vector index syntax against existing migration normalization rules.
- The implementation should avoid logging raw private Knowledge Base pages or raw message bodies in structured logs.
- The implementation should keep all page and chat queries explicitly scoped by `userId`.
- The implementation should avoid Skool-specific terms in product UI and database names.

# Execution Task Deep Validation Data Collection

## Overview

This document describes the process for collecting structured data about execution code tasks that completed with Deep Validation Reports. The reports are generated by the orchestrator's `ExecutionDeepValidator` service and posted as PR comments.

## Background

### What is a Deep Validation Report?
A post-execution audit that:
- Analyzes the full session transcript of execution agents
- Verifies claims against transcript evidence
- Checks skill contract fulfillment (executing-plans → requesting-code-review → code-reviewer dispatch)
- Compares Linear issue requirements vs delivered code
- Reports anomalies (fabrication, ignored errors, laziness)
- Posts results as a GitHub PR comment

### When Did This Start?
- First reports appeared: 2026-03-10
- Tabular format enforcement (commit `6f3e20b3f`): 2026-03-11 ~17:00 UTC
- Reports before this date may use older bullet-list format

## Data Schema

### ExecutionTaskRecord

```typescript
interface ExecutionTaskRecord {
  // Identifiers
  taskId: string | null;           // UUID from branch (task_<uuid>), null if feature branch
  linearIssueId: string;           // INT-XXX from PR title
  prNumber: number;                // GitHub PR number
  prUrl: string;                   // Full GitHub PR URL

  // Task metadata
  title: string;                   // PR title
  branchName: string;              // task_<uuid> or feature/int-xxx
  linesChanged: number;            // additions + deletions
  filesChanged: number;            // Number of files modified
  complexityScore: 1 | 2 | 3 | 4 | 5;  // Based on lines changed

  // Model data (from Firestore code_tasks collection)
  workerType: string | null;       // Model used: 'opus', 'sonnet', 'minimax', 'glm', 'qwen', 'kimi', 'codex', 'codex-xhigh', 'auto' (terminal value — not resolved further), or null if Firestore lookup failed

  // Deep validation report data
  deepValidation: {
    costUsd: number | null;        // LLM cost from report
    overallOutcome: string;        // "Implemented", "Partially achieved", "Failed"
    overallSeverity: "pass" | "warning" | "critical";

    // Claim verification
    claimsVerified: number;        // Count of verified claims
    claimsContradicted: number;    // Count of contradicted claims
    executingPlansInvoked: boolean;     // Was executing-plans skill used?
    requestingCodeReviewInvoked: boolean;  // Was requesting-code-review skill used?

    // Contract verification
    codeReviewerDispatched: boolean;  // Was code-reviewer subagent dispatched?
    orderCorrect: boolean;            // true iff both executing-plans-first AND requesting-code-review-second rows are "Compliant"

    // Anomalies
    anomaliesCritical: number;     // Count of 🔴 critical anomalies
    anomaliesWarning: number;      // Count of 🟠 warning anomalies
    anomaliesMinor: number;        // Count of 🟡 minor anomalies
    anomalyTypes: string[];        // Anomaly descriptions (may be full sentences, not short tokens)
    anomalySeverityUnavailable: boolean;  // true if Anomalies table lacked a Severity column
  };
}
```

### Complexity Scoring

| Score   | Lines Changed   | Typical Tasks                               |
| ------- | --------------- | ------------------------------------------- |
| 1       | <20             | Fix typo, single test, config update        |
| 2       | 20-100          | Bug fix with tests, small feature           |
| 3       | 100-300         | New endpoint, module refactor               |
| 4       | 300-500         | Service integration, significant feature    |
| 5       | >500            | Multi-service feature, architectural change |

## Collection Process

### Coordinator Responsibilities

The coordinator (main agent) owns the entire collection:

1. **Fetch Comments**: Get all Deep Validation Report comments from GitHub API
2. **Fetch PR Details**: Get PR metadata for each comment
3. **Batch**: Split into groups of 10 comments
4. **Dispatch**: Spawn parsing agents for each batch
5. **Aggregate**: Collect all agent outputs
6. **Validate**: Check for completeness and correctness
7. **Output**: Write final JSON file

### Phase 1: Fetch Comments

```bash
gh api "repos/pbuchman/intexuraos/issues/comments" \
  --paginate \
  -q '.[] | select((.body | test("^### Deep Validation Report")) and .created_at >= "2026-03-11T17:00:00Z") | {pr_number: (.issue_url | split("/") | .[-1]), created_at, author: .user.login, body}'
```

**Filter criteria:**
- Body starts with: `### Deep Validation Report` (anchored match avoids false positives from bot follow-ups that merely reference the report)
- Date: >= 2026-03-11T17:00:00Z (tabular format deployment)

**Note on author:** DVRs are posted by the orchestrator's `ExecutionDeepValidator` service. The actual GitHub author depends on the authentication context at post time — it may be `pbuchman` or `intexuraos-code-worker[bot]`. The filter intentionally does **not** constrain by author; instead, the anchored body regex (`^### Deep Validation Report`) is the authoritative discriminator. The `author` field is captured in output for auditing.

### Phase 2: Fetch PR Details

For each unique PR number:
```bash
gh pr view <number> --repo pbuchman/intexuraos --json number,title,headRefName,url,additions,deletions,changedFiles
```

### Phase 3: Fetch Task Records from Firestore

For each unique taskId (from branch name `task_<uuid>`) or PR number (for feature branches), fetch the document via per-document `gcloud` read:

```bash
# Per-document lookup (NOT gcloud firestore export, which is a bulk GCS export)
gcloud firestore documents get \
  "projects/intexuraos-dev-pbuchman/databases/(default)/documents/code_tasks/{taskId}" \
  --project=intexuraos-dev-pbuchman
```

Alternatively, use the Firestore REST API:
```bash
# REST API per-document fetch
curl -s -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://firestore.googleapis.com/v1/projects/intexuraos-dev-pbuchman/databases/(default)/documents/code_tasks/{taskId}"
```

For feature branches (no taskId), query by `prNumber` field using a structured query.

**Error handling for Firestore lookups:** If the document is not found (404), auth fails, or a network error occurs, set `workerType: null`, log the error with the taskId/prNumber, and continue processing. This ensures Firestore failures don't block the entire collection.

**Extract `workerType` field** - this is the model used:
- `opus` → Claude Opus 4
- `sonnet` → Claude Sonnet 4
- `minimax` → MiniMax
- `glm` → GLM
- `qwen` → Qwen
- `kimi` → Kimi
- `codex` → Codex
- `codex-xhigh` → Codex XHigh
- `auto` → Auto-selected model; treat as a terminal value in the dataset (the orchestrator resolved it at dispatch time, but the resolved model is not stored back on the task record)

### Phase 4: Prepare Input for Agents

Combine each comment with its PR details AND Firestore task data:
```json
{
  "pr_number": 1180,
  "created_at": "2026-03-14T00:11:49Z",
  "body": "### Deep Validation Report...",
  "prDetails": {
    "title": "[INT-842] Fix...",
    "headRefName": "task_c02f26c4-02aa-40dd-af5c-ac83ffdd373f",
    "url": "https://github.com/pbuchman/intexuraos/pull/1180",
    "additions": 1,
    "deletions": 1,
    "changedFiles": 1
  },
  "taskDetails": {
    "workerType": "opus"
  }
}
```

### Phase 5: Batch & Dispatch

- Split comments into batches of 10 (sized to fit within agent context windows — each DVR comment averages ~2K tokens, so 10 reports + parsing instructions stays well under the 128K limit while maximizing throughput)
- Spawn one agent per batch
- Agent uses instructions in `agent-parse-deep-validation.md`
- Each agent returns array of parsed records

### Phase 6: Aggregate

Collect all outputs into single array.

### Phase 7: Validate

Check each record:
- [ ] `prNumber` is present and valid number
- [ ] `linearIssueId` matches pattern `INT-XXX`
- [ ] `complexityScore` is 1-5
- [ ] `workerType` is present (from Firestore) or explicitly `null` with a logged Firestore error
- [ ] All `deepValidation` fields are present
- [ ] No duplicate `prNumber` entries — if a PR has multiple DVRs (e.g., re-execution), keep only the **latest** by `created_at` and discard earlier entries

### Phase 8: Output

File: `docs/plans/execution-tasks-deep-validation.json`

```json
{
  "collectedAt": "2026-03-30T...",
  "totalReports": 123,
  "dateRange": {
    "from": "2026-03-11T17:00:00Z",
    "to": "2026-03-30T..."
  },
  "tasks": [
    { /* ExecutionTaskRecord */ },
    ...
  ]
}
```

## Parsing Agent Instructions

See: `agent-parse-deep-validation.md`

The parsing agent receives pre-fetched data and returns structured JSON. It does NOT:
- Query Firestore
- Query Linear API
- Make any external calls

All required data is provided in the input.

## Report Format Reference

### Tabular Format (post 6f3e20b3f)

**Note:** Column layouts vary across the date range. The parsing agent handles multiple formats.

#### Overall — Two known formats:
- Three-column: `| Key | Result | Severity |` (2026-03-14 onward)
- Two-column: `| Key Info | Value |` (some 2026-03-13 reports)

#### Anomalies — Multiple known formats:
- `| Anomaly | Transcript Reference | Severity |` (has severity data)
- `| Anomaly Type | Description |` (no severity — set counts to 0)
- `| Message ID | Anomaly Type | Description |` (no severity — set counts to 0)
- Bullet-list format (pre-tabular, should not appear after cutoff)

```markdown
### Deep Validation Report

**Cost:** $0.013837

#### Overall
| Key     | Result      | Severity |
| ------- | ----------- | -------- |
| Outcome | Implemented | 🟢 Pass  |

#### Claim Verification
| Claim                                 | Transcript Evidence   | Result   | Severity |
| ------------------------------------- | --------------------- | -------- | -------- |
| `superpowers_executing_plans`: "used" | MSG-010: Skill called | Verified | 🟢 Pass  |

#### Contract Verification
| Requirement                         | Transcript Evidence | Result    | Severity |
| ----------------------------------- | ------------------- | --------- | -------- |
| `code-reviewer` subagent dispatched | Agent dispatched    | Compliant | 🟢 Pass  |

#### Plan vs Reality
| Requirement | Transcript Evidence | Result | Severity |
| ----------- | ------------------- | ------ | -------- |

#### Anomalies
| Anomaly              | Transcript Reference    | Severity   |
| -------------------- | ----------------------- | ---------- |
| Excessive Grep calls | MSG-092 through MSG-457 | 🟠 Warning |
```

### Branch Name Patterns

| Pattern           | Meaning               | taskId       |
| ----------------- | --------------------- | ------------ |
| `task_<uuid>`     | Execution task branch | Extract UUID |
| `feature/int-XXX` | Feature branch        | `null`       |

### Linear Issue ID Patterns

Look for in PR title:
- `[INT-XXX]` — standard format
- `INT-XXX:` — alternative format

## Validation Rules

1. **Skip non-reports**: Comments that don't match the `^### Deep Validation Report` body pattern (bot follow-ups, linear linkbacks, etc.)
2. **Date filter**: Only reports after tabular format deployment
3. **Completeness**: All required fields must be present
4. **No duplicates**: One record per PR number

## Error Handling

| Error                            | Action                                                  |
| -------------------------------- | ------------------------------------------------------- |
| PR details fetch fails           | Skip comment, log error                                 |
| Firestore lookup fails (Phase 3) | Set `workerType: null`, log error with taskId, continue |
| Parse fails for section          | Use sensible defaults, continue                         |
| No Linear issue ID in title      | Set to "UNKNOWN"                                        |
| taskId not in branch name        | Set to `null`                                           |
| Duplicate `prNumber` detected    | Keep latest by `created_at`, discard earlier            |

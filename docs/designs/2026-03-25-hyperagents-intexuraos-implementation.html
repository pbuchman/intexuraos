IntexuraOS x HyperAgents

Detailed implementation map for turning the current agent stack into a self-improving control plane

This page translates the HyperAgents paper into concrete IntexuraOS changes. The focus is not "add more agents". The focus is to make the existing task and meta layers reusable, measurable, and improvable across runs: memory, performance tracking, archive-based exploration, and transfer across coding and research domains.

Phase 0 implementation checklist

  • Define a shared versioned decision envelope structure for memory, routing, plan, verifier, and research strategy outputs.
  • Store every meta-decision with source task, policy version, confidence, and result outcome fields.
  • Add thin repository interfaces first, then pick Firestore document shapes per proposal instead of hardwiring storage inside use cases.
  • Keep all self-improving behavior recommendation-first until outcome tracking is stable enough for stronger automation.
  • Expose decisions in UI as compact cards: what was applied, why it was chosen, and whether it helped.

1. Execution Memory Graph

Persist reusable execution lessons from every attempt, then inject the most relevant lessons into future planning, execution, review, and the code-task UI. This is the most direct HyperAgent implementation because it converts evidence from one run into an improved improvement mechanism for later runs.

Complexity 6/10 Delivered Value 9/10 Future Potential 10/10
New collections: execution_memories, execution_memory_hits Prompt input: matchedMemories[] UI output: memory hits, confidence, applied lessons
1. Task finishes

Execution, review, or planning attempt completes with transcript, metrics, verifier result, and Linear context.

Existing evidence already exists in orchestrator and code-agent.
2. Memory distillation

A new distiller extracts failure mode, touched files, issue shape, winning commands, and verification blockers.

Best run after webhook finalization, not inside the worker.
3. Memory graph write

Store typed lessons plus embeddings or keyed facets by repo, label, file area, review type, and outcome.

Needs a repository and similarity lookup strategy.
4. Future task retrieval

Before planning or execution dispatch, fetch top matching memories and rank them by recency, similarity, and trust.

Dispatch becomes memory-aware.
5. Prompt injection

Add "relevant prior lessons" into planning, execution, and review system prompts with provenance tags.

Only inject the few highest-signal memories.
6. UI feedback loop

Show which lessons were used, whether they helped, and let later validation vote them up or down.

Turns memory quality into a measurable asset.

  • The execution prompt includes both lessons with task provenance.
  • The task header shows "2 prior lessons applied".
  • Deep validation scores both lessons as useful, improving future ranking.

2. Adaptive Dispatch Policy

Replace simple rule-based worker selection and fixed review routing with a policy layer that learns from task outcomes, machine health, cost, latency, and issue shape. This upgrades the current meta-agent from "route by static rules" to "route by learned evidence".

Complexity 5/10 Delivered Value 8/10 Future Potential 9/10
New collection: dispatch_policy_stats Output fields: chosen worker, retry budget, review set, confidence UI surface: inbox action review and code-task header
1. Action or issue arrives

Input comes from WhatsApp, inbox execution, or Linear auto-trigger.

Current path is mostly explicit worker preference or auto.
2. Feature extraction

Build a task profile from labels, repo, service area, estimated file count, urgency, and active-worker health.

Keep the first feature set deterministic.
3. Policy scoring

Use prior outcomes to score worker type, review depth, queue priority, and retry budget.

This is the meta-layer decision point.
4. Dispatch plan

Create a routing decision object with rationale, confidence, fallback worker, and review types.

Persist the decision for later evaluation.
5. Execution and review

Worker runs with policy-selected settings. Review types and queue behavior are no longer static.

Low-risk UI tasks can be cheaper; high-risk backend tasks can be stricter.
6. Feedback writeback

Store cost, duration, verifier failures, and PR outcome back into policy stats to improve future decisions.

Needed for transfer and policy correction.

System behavior today

A risky backend auth task and a trivial label-color UI fix both end up on similar paths unless the user explicitly writes "use sonnet" or similar.

  • Worker selection is shallow.
  • Review depth is mostly static.
  • Latency and failure history do not shape the route.

System behavior after the change

The auth task gets a stronger worker, higher retry budget, and security plus architecture review. The UI fix gets a cheaper worker and lighter review.

  • Inbox shows "routed by policy v2.3: backend auth risk + prior failure rate".
  • Code task header shows selected worker and fallback worker.
  • Future outcomes directly improve the next route.

3. Plan Archive for Complex Issues

Turn planning for complex-task Linear issues into an archive-based exploration loop: produce multiple plan variants, score them, select the best one for execution, and retain the archive so later complex issues can reuse successful decomposition patterns.

Complexity 8/10 Delivered Value 7/10 Future Potential 10/10
New collections: plan_variants, plan_variant_scores Archive concept: parent issue -> plan set -> selected variant -> execution lineage Safety gate: no multi-variant execution without explicit selection policy
1. Complex issue enters planning

A planning-task or complex-task issue with children reaches the planning path.

Current system generally creates one plan and stops.
2. Variant generation

Planner creates 2-3 decomposition variants: different subtask splits, branch strategies, or review strategies.

Cap the count to keep cost bounded.
3. Variant scoring

Rank variants using prior archive outcomes, dependency shape, expected conflict risk, and verification burden.

Score both value and execution risk.
4. Selected plan becomes active

The winning plan creates the active implementation lineage, child tasks, and planning PR references.

Only one plan proceeds to execution.
5. Execution feedback

Task outcomes write back into variant quality: did this decomposition reduce retries, conflicts, and missing requirements?

Archive quality grows over time.
6. Reuse on future issues

Similar future issues can start from an archived decomposition template instead of a blank planning pass.

This is the archive effect from the paper.

System behavior today

A large issue spanning API, Firestore, UI, and notification changes gets one plan. If the split is weak, the whole execution path inherits the weakness.

  • No plan alternatives are retained.
  • No decomposition quality score exists.
  • Future similar issues do not reuse the successful split.

System behavior after the change

The planner proposes three decompositions: service-first, workflow-first, and UI-last. The scorer selects workflow-first because similar archive entries had fewer merge conflicts and cleaner review passes.

  • The selected variant creates child tasks and a planning PR.
  • The rejected variants stay archived for future reference.
  • The next similar issue can start from the successful pattern instead of rediscovering it.

4. Self-Tuning verifier and review contracts

The current verifier and deep-validator layer is strong, but mostly fixed. HyperAgent thinking says this meta-layer should improve too. The safe implementation is offline and approval-gated: analyze old transcripts, generate candidate verifier prompts and schemas, replay them against a benchmark corpus, and only then promote them.

Complexity 7/10 Delivered Value 8/10 Future Potential 9/10
New collections: verification_experiments, verification_corpus Active config: prompt version manifest plus benchmark score Safety mode: offline replay only, human promotion required
1. Build a corpus

Collect finished task transcripts, final PR outcomes, human review comments, and verifier false-positive cases.

This becomes the benchmark set.
2. Candidate generation

A research-style analyzer proposes new verifier prompts, schemas, and section rules from the corpus.

Do this outside the live task path.
3. Replay harness

Run candidate versions against held-out transcripts and compare precision, recall, retry rate, and reviewer agreement.

Needed to reject regressions.
4. Human approval gate

Only promote candidates that beat the current version and stay within guardrails for false positives and false negatives.

No auto-promotion in early phases.
5. Production use

Live tasks reference a prompt manifest and attach verifier version metadata to all tasks and PR comments.

Allows comparison across releases.
6. Benchmark refresh

New transcripts and reviewer disagreements expand the benchmark corpus over time.

The meta-layer now learns from itself.

System behavior today

The verifier flags some missing evidence correctly, but prompt tuning is manual and hard to evaluate across old transcript sets.

  • Prompt improvement is manual craftwork.
  • Regression checking is weak.
  • False retries are hard to compare across prompt versions.

System behavior after the change

A candidate verifier prompt generated from the benchmark corpus reduces false retries by 14% while preserving missed-requirement detection, then gets promoted as verifier v4.2.

  • Every task records its verifier version.
  • PR comments can be compared by ruleset version.
  • The meta-layer improves with evidence instead of intuition.

5. Research Domain Memory

Extend the HyperAgent pattern beyond coding. Research should remember which provider bundles, synthesis heuristics, source preferences, and repair patterns worked best per domain, then reuse that strategy memory in future research, page summarization, and data-insight analysis.

Complexity 6/10 Delivered Value 7/10 Future Potential 9/10
New collection: research_strategy_memory Reusable outputs: provider bundle, synthesis tone, source priorities, repair hints Consumers: research-agent, web-agent, data-insights-agent
1. Research starts

A prompt arrives and the current context inferrer determines domain, time scope, language, and safety mode.

This already exists in research-agent.
2. Strategy recall

Look up domain memory: which models worked well, what source mix helped, and what synthesis repairs were common.

Domain memory becomes the meta-layer.
3. Bundle selection

Select or recommend provider combinations, prompt framing, and synthesis model using the recalled strategy memory.

Can be automatic or a recommendation first.
4. Research and synthesis

Models run, low-quality responses get flagged, and attribution repair happens as usual.

Existing pipeline stays intact.
5. Strategy update

Write back what worked: confidence, low-quality rate, contradiction rate, share success, export success, user retries.

Needed for transfer across runs.
6. Cross-domain reuse

The same strategy memory can inform web-agent summarization and data-insights-agent chart analysis.

This is the cross-domain transfer path.

A regulatory research prompt, a product strategy prompt, and a multilingual source-summary job all rely on isolated prompt logic with little memory of what worked before.

  • Cross-domain transfer is weak.

A new EU regulation prompt automatically recommends a provider bundle and source preference pattern that previously produced the highest-quality, lowest-contradiction outputs for official-document research.

  • The research header shows "strategy pack: regulation-primary-source-v3".
  • The same pack helps web-agent summarize linked regulator pages more effectively.
  • data-insights-agent can reuse domain phrasing and evidence handling in its chart explanations.

Recommended rollout roadmap

The right order is the one with the highest leverage and lowest system risk. Start where evidence already exists and where the web app can expose value immediately. Push archive-style exploration and cross-domain transfer into the second wave.

Recommended implementation order

PriorityImprovementWhy now
1Execution Memory GraphHighest leverage, strongest fit to existing transcripts and verifier outputs, immediate user-visible payoff.
2Adaptive Dispatch PolicyLow-risk extension of current routing, with direct cost and latency gains.
3Self-Tuning verifier and review contractsStrong value, but only after a benchmark corpus exists from phases 1 and 2.
4Plan Archive for Complex IssuesHigh upside, but more invasive across planning, child-task creation, and UI.
5Research Domain MemoryImportant second-wave transfer story after the coding loop proves out.

Safety and design constraints

  • Do not let live systems self-modify prompt contracts without offline replay and human approval.
  • Keep user-entered worker hints and model choices as explicit overrides in early versions.
  • Limit plan-variant exploration to a small bounded count and select only one winner for execution.
  • Persist version metadata for policies, verifier prompts, and memory injection so regressions remain debuggable.
  • Expose all meta-decisions in the UI. A hidden meta-layer will not be trusted.
HyperAgents in this codebase should be implemented as a progression from observable system -> reusable memory -> decision policy -> archive -> transfer. IntexuraOS already has the task agents. The missing layer is durable meta-knowledge that changes how the next task is solved.

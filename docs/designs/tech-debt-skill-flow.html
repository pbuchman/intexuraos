Tech Debt Triage Skill

Decision flow for consolidating technical debt into actionable Linear issues

Phase 1 — Pre-Flight Gates
Gate Step 1: Freshness Warning
Display AskUserQuestion warning the user:
  • This skill analyzes existing tech debt docs only, not the actual codebase
  • It assumes all technical-debt.md files are up to date
  • This skill is designed for a single run — consecutive runs will create duplicate Linear issues
Confirmed → continue Declined → STOP
Phase 2 — Discovery & Scanning
Action Step 2: Scan All Tech Debt Files
Read all technical-debt.md files:
  • docs/services/*/technical-debt.md (apps + workers)
  • docs/packages/*/technical-debt.md (shared packages)
Parse summary tables, code smells, TODO comments, SRP violations, future plans, and resolved issues from each.
Action Step 3: Extract & Classify Issues
For each issue found, extract:
  • Title — what the issue is
  • Service(s) — which component(s) are affected
  • Severity — Critical / High / Medium / Low
  • Category — TODO, Code Smell, SRP, Coverage Gap, Deprecation, TypeScript
  • Source file — path to the technical-debt.md that reported it
Phase 3 — Severity Selection
User Input Step 4: Select Severity Levels
Display AskUserQuestion (multiSelect) showing issue counts per severity:
  • Critical (N issues)
  • High (N issues)
  • Medium (N issues)
  • Low (N issues)
User selects which severity levels to proceed with.
Selected levels → filter issues None selected → STOP
Phase 4 — Consolidation & Grouping
Action Step 5: Consolidate Cross-Service Issues
Group issues that should be solved together:
  • Same pattern across services — e.g. "missing logIncomingRequest()" in 4 services → 1 consolidated issue
  • Client/server mismatch — e.g. API contract mismatch between producer and consumer → 1 issue covering both sides
  • Shared infrastructure debt — e.g. dead Pub/Sub publisher + unused Terraform resources → 1 cleanup issue
Each consolidated issue gets:
  • A clear title describing the cross-cutting concern
  • List of all affected services/packages
  • References to all source technical-debt.md files
  • Brief analysis (NO fix design — just scoping)
Phase 5 — User Approval
User Input Step 6: Approve Issues One by One
Present each consolidated issue via AskUserQuestion (multiSelect) for approval:
  • Issue title + affected services
  • Severity + category
  • Brief scope description
User checks which issues to create in Linear.
Approved items → create in Linear All rejected → STOP
Phase 6 — Linear Issue Creation
Linear Step 7: Create Parent Issue
Create top-level Linear issue via mcp__linear__create_issue containing:
  • When — date the analysis was performed
  • What — summary of all technical debt issues found
  • Where — which services/packages were analyzed
  • Scope — severity levels included
  • Count — N approved subtasks to follow
Linear Step 8: Create Subtasks
For each approved issue, create a Linear subtask under the parent:
  • Title — descriptive issue title
  • Description — brief analysis + affected services
  • References — links to source technical-debt.md file(s)
  • Ready for — direct execution via /linear INT-XXX
No fix design included — subtasks are scoped for autonomous agent execution.
Output Done
Summary displayed to user:
  • N tech debt files scanned
  • N issues found → N consolidated → N approved → N created in Linear
  • Link to parent Linear issue
Early Exit Points
Stop Step 1 Declined
User did not confirm freshness assumption. Skill exits with no action.
Stop Step 4 Empty
No severity levels selected. Skill exits with no action.
Stop Step 6 All Rejected
User rejected all consolidated issues. Skill exits with no action.

Legend

Gate — User confirmation required Action — Automated analysis User Input — AskUserQuestion Decision — Branch point Linear — Issue creation via MCP Output — Final result
